# @pb/site

The Portfolio Beach website: a static landing page with an overview of the tool, a feature tour with real screenshots, the controls it enforces, demo videos, brochures and the interactive demo itself. Synthetic data only, as everywhere in this repository: no real firm, fund, company or person appears.

It is a plain static folder. Every URL in it is relative, it asks nothing of any other origin (no CDN, no web font service, no analytics), and it works from any base path on any static host.

```bash
pnpm --filter @pb/site build            # everything, in order (about ten minutes)
pnpm --filter @pb/site build:site-only  # the pages only, with the committed media (no browser needed)
pnpm --filter @pb/site build:artifact   # the private preview: a fragment and its files, in dist-artifact
pnpm --filter @pb/site check            # the built site, served from a sub-path, in headless Chromium
pnpm --filter @pb/site check:artifact   # the same checks over the fragment inside a host document
pnpm --filter @pb/site serve            # look at apps/site/dist on http://127.0.0.1:4173/
pnpm --filter @pb/site start            # Vite dev server for the page (media must exist)
```

## What is in it

| Part | Where |
|---|---|
| The words | `src/content/site.ts`. One file, with the rules for it at the top: say only what the repository shows is built, mark the rest as planned or in progress, no number that is not in the repository, no real name, no em dashes. It also holds the site's one setting, `SITE.findable` (see "Search engines" below). |
| The page | `src/render/` builds the markup when Vite builds (`vite.config.ts`); the browser renders nothing. `src/styles/site.css` is the stylesheet, `src/main.ts` the small behaviours (theme switch, menu, lightbox). The page is complete without script. |
| Colours and fonts | `scripts/lib/tokens.mjs` derives every colour from `config/brand.json`, light and dark, with the same kind of formulas as the web app's theme. The stylesheet, the brochures and the video captions read those custom properties and write no colour of their own. |
| The 404 page | `src/render/not-found.ts`: one self-contained file, since a host serves it at whatever address was not found. It carries the two weights of the bundled face it sets inside itself, as data, so it is in the product's type without asking for a file. Its link goes to `/`; set `PB_SITE_BASE=/some/path/` at build time when the site lives under a sub-path. |
| The demo | The interactive preview of the web app (`apps/web/dist-preview`), copied to `dist/demo/` at build time. "Open the demo" goes to `demo/index.html` in a new tab (`target="_blank" rel="noopener"`), so the site stays open behind it. |

Sections of the page: hero, overview (what it brings together, who uses it, how the work flows), feature tour (nine areas and the roadmap), controls and security, demo videos, brochures, the demo, footer.

## The media is generated by script, and committed

Everything visual comes from the interactive preview by script, so it can be made again when the tool changes. The output lives in `media/` and is committed, because the host's build cannot run a browser (see "Publishing"). The build copies into `dist/media/` the files the page shows, and nothing else of that folder.

Keep the folder lean: every regeneration adds its size to the repository's history. Only screenshots that the page or a brochure shows are taken, the large file of each is written at a lower WebP quality, and each recording is encoded a second time at a lower bitrate. After the tool changes, run the full build, look at the result, and commit `apps/site/media` in a commit of its own.

| Script | Makes |
|---|---|
| `scripts/capture-screens.mjs` | Screenshots at 1440 by 900 with a device scale factor of 2, light theme, each taken as the mock user who holds the role for that screen. WebP at two widths, plus `media/screens/manifest.json`. `--only name,name` retakes some. |
| `scripts/record-demos.mjs` | Six recordings at 1280 by 720 with Playwright `recordVideo`: a title card, a caption bar that says what is happening, a visible pointer and pauses long enough to read each caption. Each caption is also spoken by an open-source voice that runs on the machine (see "Narration"), which makes a recording up to a minute and a half long. WebM (VP8), a poster frame each, and a manifest with every recording's length, size and captions (the page prints the captions as a text list). Each file is then encoded again as VP8 at a constant quality under 480 kbit/s, by the ffmpeg that Playwright installs beside its browsers (`PB_FFMPEG` points at another; without one the file is kept as Chromium wrote it, about twice the size). `--only name` records one; `--frames <dir>` writes a still per caption to look at; `--no-compress` skips the second encoding. |
| `scripts/make-brochures.mjs` | The HTML templates in `brochures/` rendered to Letter-size PDFs with `page.pdf()`, a cover thumbnail each, and a manifest with the page counts. The template follows the site's look (`docs/06` section 5): a plain cover closed by a hairline, labels in sentence case, a state as a dot and a word, no scene and no pill. It fails when a sheet's content would run past its footer. `--pages <dir>` writes every sheet as a PNG; `--ui-font "DejaVu Sans"` renders with another font to see that the sheets still fit. |
| `scripts/shoot-site.mjs` | Screenshots of the built site itself (desktop and phone, light and dark, whole page and each section), for looking at the design. They go to `--out <dir>`, or to the system's temporary folder: never into `media/`. |

`scripts/build.mjs` runs them in order: the preview when it is missing (`apps/web/scripts/build-preview.mjs`, after `tsc -b`), the screenshots, the recordings, the brochures, `vite build`, the copy of the demo, and the employer-data guard over the built folder. Pass `--fresh-preview` after the web app changed, so the media is taken from a new preview.

### Narration

`record-demos.mjs` gives each recording a voice track that reads its captions (decision 0020). The voice, the pace, the spoken form of a few terms and the model files with their SHA-256 values are in `narration.config.json`; `scripts/narrate.py` speaks the captions and `scripts/lib/narration.mjs` lays the clips under the picture at the times the captions appear. Nothing is sent to a service.

- It needs `uv` (the script lists its own dependency, `kokoro-onnx`) and an `ffmpeg` on the PATH that can write Opus (`PB_FFMPEG_AUDIO` names another). The one Playwright installs has no audio.
- Playwright records with the ffmpeg build its own version names (`ffmpeg-<build>/ffmpeg-linux` under its browsers folder) and, from 1.65, asks it for VP9. Where only an older build is installed, the recording comes out empty with no error from Playwright; point `PLAYWRIGHT_BROWSERS_PATH` at a folder whose `ffmpeg-<build>/ffmpeg-linux` is a link to an ffmpeg that has `libvpx-vp9` (the system's, say), with `PW_CHROMIUM_PATH` naming the browser. The second encoding still writes VP8, which is what the site ships.
- The first run downloads the model files (about 350 MB) into `apps/site/.cache`, which is ignored, with the clips. `PB_VOICE_MODELS` and `PB_NARRATION_CACHE` move them; `PB_NARRATE_PYTHON` names an interpreter that already has the engine.
- `--no-narration` records without sound, as before.
- To change the voice, edit `voice` and `lang` in `narration.config.json` and record again.

The scripts need Chromium. `PW_CHROMIUM_PATH` points at one; otherwise Playwright's own is used (`pnpm --filter @pb/site exec playwright install chromium`), or the preinstalled build of a cloud sandbox.

Two things to know about the recordings and screenshots:

- The tool, the site and the brochures are set in the bundled face (`apps/web/src/app/fonts.css`, decision 0026; `brochures/brochure.css` imports it as the site's stylesheet does), so screenshots, recordings and PDFs look the same whichever machine made them. `--ui-font` still renders the brochures in a wider face, to see that every sheet would fit one.
- A recording plays slightly longer than the script ran: Playwright writes every screen update as at least one frame at 25 frames a second, so anything that paints faster is slowed. The lengths the page shows are read from the files.

## Checks

`pnpm --filter @pb/site check` serves `dist` from `/portfolio-beach/` and fails on any of: a URL in `index.html` that is not relative; a link or asset that does not resolve; a request to another origin; a missing section, alt text or prototype notice; a video without a poster, a playable WebM source or its list of steps; a brochure link that is not a PDF; a text and background pair of the tokens under 4.5 to 1 (light and dark); a serious or critical axe finding on the landing page or the 404 page, light and dark, at 1440 and 390 pixels wide; a horizontal scroll at either width; a demo link that does not open a new tab with `rel="noopener"`; a demo that does not open, sign in and render the portfolio from the sub-path; a page without the `noindex` tag while the site is not switched to findable.

`pnpm --filter @pb/site check:artifact` runs the same checks over the private preview build (see below), with the fragment placed in the `<body>` of a minimal host document, and adds its own: the fragment's shape and order, `publish.json`, the limits on file size and count, the address of the demo, the background on `<body>` and the theme following the host's root element.

The repository's own gates cover the source: `pnpm typecheck`, `pnpm lint`, `bash scripts/check-style.sh` and `bash scripts/check-employer-data.sh` (stage new files first: both read tracked files).

## Hosting the folder

`apps/site/dist` is the whole site. Any static host will do: upload the folder as it is and point the host at it.

- Serve `index.html` for a directory address, with the right content types for `.webp`, `.webm` and `.pdf`.
- Serve `404.html` with status 404 for an address that matches no file, if the host offers that.
- No rewrite rule is needed. The demo routes by the URL hash, so it works from a plain file server.
- The largest files are the brochures and the recordings, a few megabytes each; no file is over 12 MB.

## Search engines

Every page asks search engines not to list it, with `<meta name="robots" content="noindex">`: the landing page, the 404 page and the demo's entry page (the build adds the tag to the copy of the demo). One switch makes the site findable: set `SITE.findable` to `true` in `src/content/site.ts` and build again. The landing page and the demo then leave the tag off; the 404 page keeps it either way. The check reads the same switch and fails when a page disagrees with it. The tag covers pages only: a PDF or a recording cannot carry it.

## The private preview build

`pnpm --filter @pb/site build:artifact` writes `apps/site/dist-artifact/` (git-ignored) from the media already in `media/`. It is the landing page for a host that wraps a page in its own document:

- `artifact.html` is a fragment, not a document: no doctype and no `<html>`, `<head>` or `<body>` tag. It holds a `<title>` (`SITE.artifactTitle`), then the stylesheet link and the inline token styles, then the page's markup, then the script tag. The stylesheet sets the background on `<body>` itself, and the theme follows the `data-theme` attribute on the host's root element, or the system setting when there is none.
- The supporting files sit beside it at the paths the fragment names: `assets/` (the stylesheet and the script) and `media/` (the screenshots, posters, recordings, brochures and their covers). Every URL is relative and nothing is asked of another origin.
- `publish.json` is `{ "page": "artifact.html", "files": [ ... ] }`: every supporting file, by its path beside the fragment.
- The demo is not in the folder. "Open the demo" goes, in a new tab, to the address in the environment variable `SITE_DEMO_URL` (an absolute http or https address). Without the variable the build says so and leaves the action out of the page.
- The build fails when a file reaches 15 MB, when the folder reaches 200 files, or when the fragment names a file that is not beside it.

```bash
SITE_DEMO_URL=https://address.of.the/demo pnpm --filter @pb/site build:artifact
SITE_DEMO_URL=https://address.of.the/demo pnpm --filter @pb/site check:artifact
```

## Publishing

The owner connected this repository to Cloudflare's own build, so publishing is one thing: **a push to `main` publishes the site.** Cloudflare installs the workspace, runs the repository's build and then `npx wrangler deploy` from the repository root, which reads the `wrangler.toml` there. No token, secret or variable is needed in this repository.

What `wrangler.toml` at the repository root says:

- **The folder:** `apps/site/dist`, served as static files.
- **The build:** before it reads that folder, wrangler runs `pnpm --filter @pb/site build:site-only`: the interactive preview (recorded from the synthetic dataset, no browser needed), then the pages with the media that is committed under `apps/site/media`.
- **The domain:** one `routes` line. A publish moves that domain to this site's Worker from whichever Worker holds it, without asking. To change domains, change that line. To publish to the Worker's own workers.dev address only, set `routes = []`.
- **The name:** inside Cloudflare's build, wrangler uses the name of the connected Worker whatever the file says.

What to expect:

- **The media is committed.** Cloudflare's build cannot run a browser, so the screenshots, recordings and brochures are generated in a development session (`pnpm --filter @pb/site build`) and committed under `apps/site/media` (about 25 MB). When the tool changes, regenerate and commit them, or the site shows the old pictures. `build:site-only` works from a clean clone: it builds the interactive preview itself (no browser needed) and takes the media as committed.
- **The repository that held the domain before will take it back on its next deploy** for as long as its configuration names the domain. Its change to stop that is a pull request in that repository, to merge after this site has published.
- **Other branches do not publish.** Cloudflare builds them as previews at their own addresses; a preview never takes the domain.
- The pages carry `<meta name="robots" content="noindex">` until `SITE.findable` is set in `src/content/site.ts` (see "Search engines"), so search engines are asked not to list them.
- `.github/workflows/site.yml` only builds and checks the site (links, media, accessibility, no request to another origin) when a person starts it; it publishes nothing.

To check the configuration on a machine without credentials: `pnpm --filter @pb/site deploy:dry-run` (after a full build). It builds the pages, reads `dist`, uploads nothing and needs no account.
