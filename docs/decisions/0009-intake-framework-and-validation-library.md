# 0009: The intake framework, the validation library and the accounting import
- **Status:** Accepted for the prototype
- **Date:** 2026-10-12
- **Deciders:** repo owner (asked to continue into Phase 1); built in Claude Code
## Context
docs/04 M2 asks that nothing reaches production unvalidated: every external value lands in staging, is validated against a rule library (target 100+ rules, each with a passing and a failing test), is diffed against the current record, and is promoted only after a person approves it (SEC-9.1). The first intake is the generic accounting export of `config/accounting_layout.json`: quarterly figures and the booked fair value per investment and period. Phase 0 left the staging tables (`stg.intake_file`, `stg.intake_row`), the staging state machine (docs/18 section 2) and the local folder accounting adapter in place; nothing used them yet.
## Options considered
1. Validate inside the API's intake service with ad hoc checks. Fast, but the rules could not be reused by the preview or by the other intakes (ops drop, weekly report, look-through), and "each rule has a passing and a failing test" has no natural home.
2. A separate pure package, `packages/validation`, holding the rule library, the layout-driven file reader, linking and the diff, used by the API and by the preview shim in the browser. Chosen.
3. A rules engine with rules as data (JSON). More machinery than the prototype needs; rules in TypeScript keep the type checker and the tests close to the logic.
## Decision
- `packages/validation` is a domain package (no wall clock, no randomness, no floats: the lint config lists it with calc and workflows). A rule is `{ id, category, severity, title, check(context) }`; ids carry their category prefix (`REQ`, `TYPE`, `RANGE`, `PERIOD`, `BOUND`, `TIE`, `DUP`, `XREF`, `STALE`), the nine categories docs/04 names. `runRules` collects findings; `statusFromFindings` lands a row in `flagged` on any error and `validated` otherwise; warnings travel with the row to the reviewer. Every threshold comes from `config/definitions.json` (`intake`, `priorYearPeriodEndToleranceDays`, `unitSanityBoundsUsd`) through the API's strict readers, never from a literal in a rule (rule 9).
- The file reader is driven by the layout: an unknown column is a file-level error when the layout says so (a renamed column is never guessed at), a missing non-optional column always is, and cells stay text until a rule reads them, so a reviewer sees exactly what the file said. The layout gains an optional `CompanyName` column used for linking only when the number is blank.
- Linking follows docs/03 section 5 exactly: investment number first, then an exact canonical name or alias, never a near miss. A near miss is reported with its candidates for a person; a name on the match guard list is `guarded` and never linked whatever the similarity. These cases open `ops.data_exception` rows with the candidates.
- The diff compares the four quarterly figures as decimals against the approved quarter the row reports for (a sponsor closing a few days from the quarter end lands on the quarter, the same tolerance the rest of the system uses). The booked fair value is never written from a file: it ties to the Locked mark (`TIE-01`) and a difference is an error and an exception. Valuations keep their own workflow (decision 0006).
- Intake is idempotent by content: the SHA-256 of the file text with the source is the key of `stg.intake_file`; the same file again answers the existing record with `duplicate: true` and stages nothing.
- Approval and promotion are one transaction: `validated > approved` by the reviewer (operations or deal team, the machine's rule) then `approved > promoted` by the service actor, writing `mon.quarterly_performance` with lineage (`source_locator = intake_file:<id>/row:<n>`), approval columns, and one audit event per promoted row carrying the old and new figures (rule 6). Rows with no link cannot be approved. Rejection needs a reason (the machine's precondition).
- Linking, the diff and the rules run as the **system actor** (`core.app_user` id `...0001`, role `service`, `DbService.runAsSystem`), not as the importer: an export covers the whole book, and a walled position must link rather than read as "no match" and open a false exception for every operations user outside its wall (the seed, like a real wall, names no operations user). Migration 0008 lets the `service` role past walls in `pb.can_see_walled`; the RLS matrix gains the actor (it sees walled records; it holds no client entitlement, no wall membership and no audit or history read). The role is never a sign-in role: the API leaves a credential that carries it anonymous (`identity.middleware.ts`, tested), so only server code runs as this actor. The importer's own transaction writes the file, the rows and the exceptions under their row-level security, and the system actor audits nothing by itself: the caller's `intake.import` event is the record.
- Reviewers see the staged rows RLS lets them see: a row linked to an investment the caller cannot open is left out and counted (`hiddenRows`), never shown or refused with a 403; a candidate they cannot open is dropped from the link on read; `XREF-01` and `XREF-03` messages count candidates and name none, so a finding reads the same for everyone; and an `ops.data_exception` (readable by every authenticated user) carries a candidate's number and reason only, the names being on the staged row. Approve-all acts on the rows the reviewer sees; the walled position's row waits for a wall member (the e2e journey ends with one finishing the file).
- Security role impact: the deal team gains **update** on `stg.intake_file` and `stg.intake_row` (migration 0007) so it can approve as docs/18 section 2 says; import (insert) stays with operations and the service. Rejection is operations' call under the machine, so a wall that holds a position whose rows can be flagged needs an operations member, or the file never leaves `flagged`: the owner decides whether walls must include one or the machine lets a deal-team wall member reject (owner item). Validated rows have no reject path in docs/18 either (owner item). Exceptions open at `exception_severity.high` (the taxonomy has no intake-specific term).
- The synthetic generator ships three exports (`clean`, `update`, `defects`, docs/14 section 6) that report what they carry, so tests and the preview walkthrough assert against the generator rather than hand counts. The static preview runs the same validation library in the browser over bundled samples and recorded investment data; promotion there changes the staged rows only, never the recorded figures (the preview's standing rule).
## Consequences (security, cost, operations, migration)
Security: SEC-9.1 holds for the first intake (staging, validation, approval, then production); the import is operations only, the reads are limited to operations, deal team, approvers and auditors, and RLS applies to every table touched. The audit trail records the import (counts only), every promotion (old and new values) and every command. Cost: none. Operations: `pnpm synth:exports` fills the accounting drop folder; the local folder adapter lists it. Migration: 0007 adds a `findings` column to `stg.intake_file` and the deal team's update policies on the staging tables; 0008 lets the `service` role past walls (a one-clause change to `pb.can_see_walled`, reverted by restoring the 0002 body). The other intakes (ops drop, weekly report, look-through reconcile) reuse the same tables, the same machine, the same library and the same system-actor linking with their own rule sets and layouts.
## SEC IDs affected
SEC-9.1 (staging, validation, approval, then production), SEC-5.1 and SEC-5.3 (row-level security and walls on staged rows; the system actor sees walled records and is never a sign-in role), SEC-4.5 (a credential carrying the service role is not signed in), SEC-11.1 and SEC-11.4 (audited import, promotion and commands; details stay in the database)
## Verification
`pnpm vitest run --project validation` (a passing and a failing case per rule, the reader, linking and the diff); `pnpm vitest run --project api src/test/intake.test.ts` (the docs/04 M2 acceptance criteria: idempotent re-import, zero production rows before approval, lineage on every promoted value, near-miss names to exceptions, roles and walls); the web page tests; the e2e intake journey; the preview probe's intake steps.
