# 0010: The three remaining Phase 1 intakes, company aliases and the data exceptions queue
- **Status:** Accepted for the prototype
- **Date:** 2026-10-12
- **Deciders:** repo owner (asked to continue Phase 1); built in Claude Code
## Context
Decision 0009 built the intake framework around the accounting export: staging tables, the validation library, linking by number or exact name, the diff, approval then promotion, and data exceptions for what a person must decide. docs/04 M2 names three more intakes that reuse it, each with a different shape of file and a different end state: the weekly report values (`weekly-report-intake`: valuation staging with prior value, variance, threshold flag and reviewer decision), the look-through reconcile (`lookthrough-reconcile`: outside exposure data against the taxonomy and approved values, differences as data exceptions with an optional external ticket) and the operations workbook drop (`ops-drop-import`: workbooks parsed by template signature, unknown templates refused). docs/04 M1 asks for an alias table beside the match guards, and for the Data Health page to show open exceptions, which so far had no page and no way to be worked. This record covers the foundation of that slice: contracts, config, the migration, the adapters and the exception state machine. The services, the pages and the synthetic sources are built on it in the next waves.
## Options considered
1. One intake service with a mode switch per source. Short, but the three intakes end in different places (a Draft valuation, an exception, a quarterly figure) and a mode switch would grow into the duplication rule 7 forbids.
2. Three thin intakes over the shared framework, each with its own contract and rules, the accounting layout reused where the data is the same (ops drop), the staging table that already exists reused where the data is a valuation (weekly), and exceptions where nothing is written at all (look-through). Chosen.
3. A generic "any file to any table" mapper. More machinery than the prototype needs, and it would blur the one rule every intake shares: nothing reaches production before a person approves it.
## Decision
- **Weekly values create a Draft valuation, never a mark.** A weekly file (`InvestmentNumber`, `CompanyName`, `ReportDate`, `ReportedValue`) stages into `stg.valuation`, which migration 0010 extends with the row number, the company name, the prior's source and date, the link, the findings, the raw cells, the decision times and the valuation the approval created. Each row is compared with its prior: the latest Locked mark on or before the report date (a mark locked for a later date did not exist when the week was reported), or the weekly value promoted after that mark (`prior_source`), and the move against it is `variance_pct`; a move at or beyond `intake.weeklyVarianceThresholdPct` sets `flag = above_threshold`, a report date more than `intake.weeklyStaleDays` before the as-of date is stale. Approval (`validated > approved` by operations or the deal team, then `approved > promoted` by the system actor, the staging machine of docs/18 section 2) creates a Draft `mon.valuation` of method `valuation_method.weekly_report` through the valuation machine (`(new) > Draft`, operations). A weekly value therefore never touches a Locked mark and never reaches a report (reports read Locked only); it is a Draft that the valuation workflow carries from there. The typed columns of `stg.valuation` are nullable and `raw` keeps every cell as the file wrote it, so a row with a blank number, a date that is not a day or a value that is not a decimal is staged and flagged rather than refused, the same as the accounting intake.
- **Look-through differences open exceptions and change nothing.** A reconcile run reads the provider's extract for one as-of date (`LookThroughProvider.fetchExposures`), links each row by number or exact name, maps the provider's sector and geography labels onto taxonomy codes through `config/lookthrough_mapping.json`, and compares the mapped codes with the company's and the provider's exposures with the record's cost and latest Locked mark, within `intake.lookthroughCostToleranceUsd` and `intake.lookthroughNavTolerancePct`. Every difference, every unknown label and every unresolved link opens an `ops.data_exception` with the expected and actual texts; the approved values are never written from a provider file (docs/04 M1: outside sources are mapped to the taxonomy and never override it). A run is an `stg.intake_file` of source `lookthrough` (idempotent by the extract's content hash) whose rows carry the comparison; there are no commands on a run, differences are worked on the exceptions page. The sample mapping maps every taxonomy sector and geography code and deliberately leaves the provider's `Other` unmapped, so the reconcile has something to flag on synthetic data.
- **Ops-drop workbooks map onto the accounting layout by template signature.** `config/ops_drop_templates.json` names each template by its sheet names and the SHA-256 of its header cells (joined by the unit separator U+001F, `TEMPLATE_HEADER_SEPARATOR`), and maps each header cell onto a column of `config/accounting_layout.json`. A workbook whose signature matches a template is read as if it were the accounting export and stages through the same linking, diff and rules, with `template_signature` on the file; a workbook that matches no template is refused with a message naming its sheets and stages nothing. The detail of such a file is the existing `GET /intake/files/{id}`. The upload limit, `intake.maxWorkbookBase64Chars`, is config: `opsDropImportBody(limit)` in `@pb/contracts` builds the body schema with it, and the route table documents the shape without a limit.
- **Exceptions move through `exceptionMachine`** (docs/18 section 9): `open > acknowledged`, `open | acknowledged > resolved` and `open | acknowledged > wont_fix`, operations only, resolved and wont_fix terminal, a reason required to resolve or close. Setting the external ticket is a plain update, not a transition. Migration 0010 narrows the database to the same rule: operations alone may update an exception, and only its `state`, `owner_id` and `external_ticket` (a column grant); the figures an exception carries are written once by the intake that opened it. An exception about a staged row is readable only by someone the row's own policy admits (the select policy joins `stg.intake_row` or `stg.valuation` by entity), so a walled position's exceptions stay inside the wall without a second copy of the wall rule.
- **Aliases are exact matches only** (docs/03 section 5). `core.company_alias` holds the names a portfolio company is also known by, unique across companies so a match is never ambiguous, readable by every authenticated user and maintained by operations and platform administrators, with history. Linking tries the investment number, then the canonical name, then an alias, all exact; a near miss is still a candidate for a person. The seed loader takes an optional `companyAliases` array so older datasets still load.
- **Config and adapters.** `config/definitions.json` gains the five intake settings above with the `_note` extended; `config/lookthrough_mapping.json` and `config/ops_drop_templates.json` are read at startup against their contracts (`lookthroughMapping`, `opsDropTemplates`) and a missing or malformed file stops the process naming the path of the problem, never a value. `FileDrop` (`listFiles`, `readText`, `readBytes`) is the interface of a drop folder; `LocalFolderDrop(drop, root, extensions)` reads `<root>/in` by bare file name (no path segments, no other kinds), and `LocalFolderLookThroughProvider(root)` reads `<root>/<asOf>.json` and answers no rows for a date with no extract. `AdapterSet` gains `weeklyDrop` and `opsDrop`; the production guard refuses the three new mocks by name, and `PB_DROP_ROOT` (default `.synthetic/drops`) holds the `weekly`, `ops-drop` and `lookthrough` folders. The two drops carry kill switches (`adapter.weekly_drop`, `adapter.ops_drop`, feature flags inserted by migration 0010); the look-through folder keeps `adapter.lookthrough`.
- **Contracts.** `intakeFile.source` widens from the accounting literal to `intakeSource` (`accounting | weekly | lookthrough | ops_drop`) and gains `templateSignature`, optional and nullable until every producer sets it (the accounting intake and the preview predate it); `intakeFileListQuery` filters by source. `GET /intake/files` must filter by that query and the file detail must answer accounting and ops-drop files alike. The ten new routes and their roles are in `packages/contracts/src/routes.ts`; the API's contract parity test fails until their controllers land, which is the next wave's first job.
## Consequences (security, cost, operations, migration)
Security: SEC-9.1 holds for all three intakes (staging, a person's approval, then a Draft valuation, a quarterly figure or nothing); every new table and policy is in the RLS matrix with a walled row (`stg.valuation`), the exception queue's narrowed update and the alias writes. Cost: none. Operations: three more drop folders under `PB_DROP_ROOT`, created outside production like the others; two more kill switches. Migration: 0010 is one file with a rollback note (aliases, the staging columns and policies, the exception policies and column grant, the taxonomy term, the flags); the unique key `(report_date, investment_number)` on `stg.valuation` becomes a plain index because a file may repeat a key and the DUP rules flag it, and `(intake_file_id, row_no)` is the new unique key. Open items for the next waves: the intake service sets `templateSignature`, after which the field becomes required; the API test harness should point `PB_DROP_ROOT` at its scratch folder like the other roots (the default folders are gitignored, so the tests are harmless meanwhile).
## As built: the look-through reconcile and the exceptions queue (2026-10-14)
`POST /intake/lookthrough/reconcile` reads the provider's rows for the as-of date through the look-through adapter and hashes the date together with the rows (SHA-256 over `<asOf>\n<JSON of the rows>`), so two runs for different dates never collide even when the provider sends the same rows for both: the record is read as of each run's own date, so what was compared differs. As the system actor it links every row against the one investment directory (number, canonical name, then an alias, all exact; the match guards apply), maps the labels through the loaded `config/lookthrough_mapping.json`, reads each linked company's sector and geography codes and the position's invested cost and NAV exactly as the portfolio pages compute them (`positionMetrics` over the approved flows and the latest Locked mark on or before the as-of date; never a second derivation), and runs `LOOKTHROUGH_RULES` from `packages/validation` (`rules/lookthrough.ts`: LT-REQ-01, LT-TYPE-01, LT-XREF-01 to 03, LT-MAP-01 and 02, LT-DIFF-01 and 02, LT-TIE-01 and 02, LT-DUP-01, LT-STALE-01; the two tolerances through the module's own strict reader). The run is an `stg.intake_file` of source `lookthrough` with `as_of` set and `template_signature` null; each row of `stg.intake_row` carries the provider's row, the mapping, the record's values, the differences and the link in its payload, the natural key `number-or-name|asOf`, a diff of kind `unchanged` with no changes (nothing is written) and its status from the findings. One `ops.data_exception` opens per difference (DIFF and TIE rules, carrying the record's text and the provider's), per unmapped label (MAP) and per unresolved link (XREF, candidates by reason only), with source `lookthrough_reconcile`, severity `exception_severity.high` for TIE and XREF and `exception_severity.medium` for MAP and DIFF (the terms migration 0002 seeded); a stale or duplicate row is flagged but opens nothing, since it is neither a difference nor a link. A date the folder holds no extract for stages a run with no rows and the file finding LT-FILE-01; a file in the folder that is not an extract is a 503 and stages nothing; a date after today is refused (400) since the record has nothing to compare for it. One audit event `intake.reconcile` carries counts only; the run detail (`GET /intake/lookthrough/runs/{id}`) hides rows past the reader's wall and counts them, filters candidates per reader and is audited as a read, and the run appears in `GET /intake/files?source=lookthrough`. The exceptions queue (`GET /data-exceptions`, `GET /data-exceptions/{id}`, `POST /data-exceptions/{id}/commands`) reads under the policy of migration 0010 and adds the context a reader may see (the staged file and row, the position when the caller may open it, the owner's name); commands run with the row locked (`select for update`), a state guard on the write (409 on a race), `exceptionMachine` for acknowledge, resolve and wont_fix (acknowledge takes ownership; a command from a terminal state is a 409 `workflow-transition` by the shared refusal table; a blank reason is a 422 precondition, a missing one a 400 at the boundary), `set_ticket` as a plain update of `external_ticket`, and an audit event per command with the state before and after, the reason and the ticket. The pages Data > Look-through (run card with the as-of date from Data Health, run list, run detail with tiles and the reconciled positions) and Data > Exceptions (queue with state, source and severity filters, a run's or a file's exceptions when opened from one, and the detail page with the commands gated by the transition table) are in `apps/web/src/pages/lookthrough` and `apps/web/src/pages/exceptions`; the Data Health open-exceptions tile links to the queue.
