# 0011: A dependency-free XLSX reader and writer (`packages/xlsx`)
- **Status:** Accepted for the prototype
- **Date:** 2026-10-14
- **Deciders:** repo owner (asked to continue Phase 1); built in Claude Code
## Context
The ops-drop import (decision 0010, docs/04 M2) receives operations' quarterly figures as `.xlsx` workbooks, matches each workbook to a template by its sheet names and header cells, and stages the rows through the accounting layout. The static preview has to read the same workbooks in the browser, and the synthetic generator has to write them so the API tests, the Playwright journey and the preview samples share one set of files. Three places therefore need one workbook format: the API under Node, the preview in a browser bundle, and the generator.
## Options considered
1. A published spreadsheet library. The widely used ones either carry a large dependency tree, bundle poorly for the browser, parse every cell into a JavaScript number (which loses the exact decimal text the figure rules compare), or read the wall clock and random values when writing (which the repository's lint rules forbid in the packages that must be deterministic). Adding one also adds a supply-chain surface for the one format a security-sensitive intake accepts.
2. A hand-written reader and writer limited to what the intake needs: a zip layer (stored and deflate entries), an XML parser with depth and node budgets, and the six workbook parts. Small (about 1,500 lines with the tests beside them), fully typed, deterministic, and the same code under Node and in a browser because the inflater is injected.
3. Convert workbooks to CSV outside the system before import. Pushes work back onto operations and keeps the template signature (sheet names plus header hash) out of reach.
## Decision
Option 2. `packages/xlsx` (`@pb/xlsx`) is a dependency-free XLSX reader and writer in pure TypeScript:
- `readWorkbook(bytes, { inflateRaw, limits })` returns every sheet in workbook order with every cell as the text the file holds (a number is its stored text, never a float; a boolean is `TRUE` or `FALSE`; a formula cell gives its cached value; an error cell its error text). Shared strings, inline strings and rich text runs are read; sparse rows and columns are filled with empty text.
- The inflater is injected: `@pb/xlsx/node` provides zlib's raw inflate with `maxOutputLength`, and the preview provides `DecompressionStream('deflate-raw')` with the same guard (an entry that inflates past its declared size is refused while it is being read).
- `READ_LIMITS` bounds one read: cells per sheet and per workbook, sheets, XML depth, bytes per part and per workbook. The limits are also in `config/definitions.json` (`intake.workbookMaxCells`, `workbookMaxSheets`, `workbookMaxPartBytes`) so operations can lower them without a code change. Zip64, multi-disk archives, encryption and every compression method other than stored and deflate are refused with a plain message.
- `writeWorkbook(sheets)` writes every cell as an inline string with stored zip entries and every timestamp fixed to 1980-01-01, so the same input always gives the same bytes and nothing reads the wall clock.
- `templateKey(workbook, headerSheet)` is the template signature the ops-drop import matches on: the sheet names and the header cells joined by the record and unit separators (U+001E, U+001F), with trailing empty header cells trimmed, hashed with SHA-256 against `config/ops_drop_templates.json`.
## Consequences (security, cost, operations, migration)
Security: the one binary format an intake accepts is parsed by code the repository owns and tests, with hard limits on size, depth and cell count (SEC-10.3) and no new dependency to review under SEC-10.5. Cost: about 1,500 lines to maintain, in exchange for no library upgrade cycle and one behavior in three places. Operations: a workbook the reader refuses names the reason (a part past its limit, an unsupported method, a malformed cell reference); the limits are config. Migration: none; a published library could replace the package behind the same two functions later if the format needs grow (styles, dates as dates, formulas evaluated), which the prototype does not need. Not supported, by design: writing numbers as numbers, cell styles, dates as serials, merged cells, external links, macros.
## SEC IDs affected
SEC-9.1 (staging and validation of an intake's input), SEC-10.2 (input validation at the boundary), SEC-10.3 (file upload safety: size, part and cell limits, unsupported features refused), SEC-10.5 (no new third-party dependency for a parsing surface).
## Verification (what was checked, docs/versions consulted)
`pnpm vitest run --project xlsx`: the zip layer (stored and deflate entries, the central directory, the zip64 locator refused, a declared size that lies), the XML parser (entities, CDATA, depth and node budgets, invalid characters), cells (references up to Excel's row and column limits, escape sequences), the reader (shared and inline strings, rich text, cached formula values, sparse rows, every limit at its boundary) and the writer (byte-for-byte determinism, sheet name rules, Excel's text length limit), 73 tests. The API ops-drop suite and the Playwright ops-drop journey read workbooks the synthetic generator wrote with this package; the preview probe reads them in Chromium through the browser inflater. Format references: ECMA-376 Part 1 (SpreadsheetML, 5th edition) and PKWARE APPNOTE 6.3.x for the zip layer.
