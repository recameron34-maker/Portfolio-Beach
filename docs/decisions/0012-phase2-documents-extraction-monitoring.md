# 0012: Phase 2 plan: the document hub, AI extraction and the monitoring board
- **Status:** Accepted for the prototype (plan; as-built sections are appended as each wave lands)
- **Date:** 2026-10-15
- **Deciders:** repo owner (asked to continue along docs/09); built in Claude Code
## Context
Phase 1 is complete (decisions 0009 to 0011). docs/09 Phase 2 covers M3 (document hub and AI tagging), M4 (AI extraction with citations) and M9 (portfolio monitoring), with the exit: critical journey 2 of docs/12 passes (drop a synthetic quarterly report, extract, review flagged fields, approve, see the one-pager update with citations) and the M4 eval thresholds are met with the mock client and recorded fixtures. The data model already names the tables (docs/03: `doc.document`, `doc.expected_document`, `doc.extraction_run`, `stg.extracted_value`), the machines exist in `packages/workflows` (document classification, extraction run), the lineage columns exist on `mon.quarterly_performance`, and the adapter interfaces exist (`DocumentStore`, `AiModelClient`) with a local folder store and a mock client that never invents output. Nothing reads or writes a PDF yet, there is no prompt registry (`packages/ai`), no synthetic documents, and the monitoring board, the realization outlook edit and watchlist alert dispatch are open (docs/11 E1 to E4, E7, E8, I1).
## Options considered
1. **PDF handling through published libraries** (a writer for the generator, a parser for the worker, a renderer for the review page). Realistic, but three dependencies to review under SEC-10.5, a browser bundle the preview cannot carry whole, and a parser that reads the wall clock and random values where the repository's lint rules forbid them. The production slot for sponsor PDFs (OCR, scans, rasterized page images) is the Python document worker with IT-approved libraries, not the prototype.
2. **A dependency-free `packages/pdf`** on the pattern of `packages/xlsx` (decision 0011): a deterministic writer for text-and-lines pages and a reader that returns positioned text runs per page, with inflate injected so the API and the browser preview read a document the same way. The review page renders the page from its text layout and highlights the cited quote (click-to-source) instead of showing a raster image. Scanned variants and OCR are out of the prototype and recorded as an owner item.
3. **Skip documents, feed extraction from fixtures only.** Fails the exit journey ("drop a synthetic quarterly report") and leaves M3 unbuilt.
## Decision
Option 2, built in four waves on the Phase 1 pattern (non-overlapping worktree agents per wave, a checker per build, an adversarial review before publishing).

**Wave 1, foundation (parallel):**
- `packages/pdf` (`@pb/pdf`): `writePdf(document)` (pages of text runs, lines and rectangles; the standard 14 fonts by name, WinAnsi text; uncompressed content streams; fixed metadata; the same input always gives the same bytes) and `readPdf(bytes, { inflateRaw, limits })` (classic cross-reference tables and cross-reference streams, object streams, FlateDecode through the injected inflater, simple fonts with their encodings and Type0 fonts through ToUnicode; a run whose font cannot be decoded is returned as undecodable, never guessed; every page as positioned runs, lines grouped by baseline, and plain text). Hard limits on bytes, objects, pages, stream length and operators; encryption, JavaScript and images are refused or ignored by name. `@pb/pdf/node` provides zlib inflate; the preview provides `DecompressionStream('deflate')`.
- Migration 0011 and the schema mirror `packages/db/src/schema/doc.ts`: `doc.document`, `doc.expected_document`, `doc.extraction_run`, `stg.extracted_value` as docs/03 names them, the `doc_type.*` taxonomy (the docs/04 M3 list), `doc.document` text in a `tsvector` for full-text search, row-level security: a document, its expected-document row, its runs and its extracted values carry the wall of the investment they are attached to (`pb.can_see_walled('investment', investment_id)` where linked; sponsor-fund and unlinked documents are every authenticated user's); deal team and operations classify, operations and the service actor index and run, operations and deal team review extracted values, approval follows the staging machine's approve row; the matrix gains a walled document and its run. Config: `config/extraction_schema.json` (the fields of each document schema: key, label, kind, required, target column, range bounds), `config/definitions.json` `documents` (expected-document due days after quarter end, aging buckets, search page size) and `extraction` (batch concurrency, per-run and per-day token budgets, quote length 150, retry budget from docs/18).
- `packages/contracts`: documents (list with filters and full-text query, detail, review queue, classify command, duplicates, expected documents with aging), extraction (batch start, runs list and detail with values and page layouts, review commands: accept, edit, reject, bulk accept clean, approve and promote), monitoring (board by quarter with status and aging, status export, realization outlook edit). Routes with roles; the OpenAPI document regenerated.
- `packages/ai` (`@pb/ai`): the prompt registry (ids and versions; system prompts carrying the docs/07 universal rules and the SEC-8.3 delimiters, no tools), zod output schemas built from `config/extraction_schema.json` (every number carries value, unit, page, quote of at most 150 characters and confidence), deterministic validators (units through `packages/calc/units.ts`, range bounds, citation present and the quote found on the cited page, highlights against `config/style.json`), redaction filters (bank details, personal identifiers; SEC-8.7), the fixture-backed prototype models (a keyword classifier whose confidence comes from the evidence it finds, and an extractor that answers from the recorded truth of the document's content hash and never from the text), and the eval harness behind `pnpm test:evals` (classifier precision per type, field accuracy, unit errors, citation misses, hallucinations, injection suite) with the thresholds of docs/04 as assertions.
- `tools/synthetic` documents: quarterly report PDFs per investment per approved quarter (letter page, financial summary table, portfolio table, footnotes) written with `@pb/pdf` from the dataset's own figures, capital call and distribution notices from the capital notices, capital account statements per sponsor fund, each with a `*.truth.json` sidecar (document type, links, period, unit, every field with value, unit, page and quote, highlights, scenario tags); the docs/14 scenarios `injection_doc`, `duplicate_doc`, `untagged_doc`, `late_financials` and `restatement`; the CLI `documents` command writing the folder tree the local document store reads; the preview book carrying the sample documents it needs.

**Wave 2, API:** `apps/api/src/documents/` (index the store into `doc.document` with content hash and duplicate detection, classify through the model client with the threshold from config, the review queue and the human classify command, expected documents generated per investment and quarter with due dates and aging, search filtered by row-level security, no document extracted without an index row), `apps/api/src/extraction/` (batches as `ops.job` rows, runs through `extractionRunMachine` with the retry budget and cost logging, values into `stg.extracted_value` with validation state, the review commands, approval promoting the approved figures into `mon.quarterly_performance` with lineage columns in one audited transaction, a failed run opening a data exception, highlights drafted from approved numbers only), `apps/api/src/monitoring/` (the board: investment by quarter with status from expected documents, runs and approvals, aging; the status export; the realization outlook edit, audited; watchlist alerts as `ops.task` rows for the deal team).

**Wave 3, web and preview:** Documents hub (search, filters, detail with metadata and duplicates, the review queue, the expected-document tracker), Extraction (batch board, run review by exception: page layout beside the fields, flagged fields first, accept, edit, reject, bulk accept clean, approve), Monitoring board, the deal workspace Documents tab, click-to-source citations on the Performance tab (I1), the realization outlook edit; the preview simulating all of it client-side over the bundled synthetic documents (the PDF read in the browser, the fixture-backed models in the bundle); Playwright: critical journey 2, the search-permission test (a walled document is not found by a non-member), accessibility on every new page.

**Wave 4:** adversarial review and fixes, docs (03, 09, 11, 14, 18 where a transition is refined, SESSION_LOG), gates, the artifact republished.
## Consequences (security, cost, operations, migration)
Security: SEC-8.3 (delimited data, no tools, embedded instructions ignored; the injection suite is a release gate), SEC-8.4 (schema, units, ranges, a citation on every number; failed outputs never write), SEC-8.5 (search and the hub apply row-level security before anything is returned), SEC-8.7 (redaction before the call), SEC-8.9 (model, prompt version, tokens, latency and ids logged; never content), SEC-9.1 (staging, review, approval, then production), SEC-10.3 (the PDF reader's limits; no scripts executed), SEC-10.5 (no new dependency). Cost: `packages/pdf` is about the size of `packages/xlsx`; the fixture-backed models cost nothing to run. Operations: every run logs tokens and cost against the config budgets; the kill switch `ai.extraction` stops new runs; a failed run is a data exception. Migration: new tables only; `mon.quarterly_performance` gains no column (the extra extracted fields stay on the run, approved, and are read through the document). Out of the prototype, recorded for the owner: OCR and scanned variants, semantic search (needs an embedding service), the Python document worker as the production parser, a real model on synthetic PDFs (an approved key), CIM and primary fund extraction variants beyond the capital account statement.

## As built: the documents API (wave 2)
`apps/api/src/documents/` serves the eight hub routes. The index (POST /documents/index, operations) takes the store's inbox in a locale-free order where a plainly named item precedes its " (n)" renamed copy, and writes as the system actor inside the caller's transaction (`asSystemActor`, migration 0011: walled positions get their rows) while the caller's audit events record each change: an item already indexed under its path and hash is unchanged (changed bytes under an indexed path are logged, never rewritten); the same bytes under another path become a Duplicate through `markDuplicate`, linked to the earliest non-duplicate original and carrying its links but no type; a new item is read with `readPdf(bytes, { inflate: nodeInflate, limits: { maxBytes: documents.maxPdfBytes, maxPages: documents.maxPages } })`, inserted as Received with the Info title (else the file name without extension) and the first 2000 characters of text, then classified when `ai.classifier` is on: every page redacted, the input built by `buildInput`, one `document_classifier` call logged by prompt id, version, model, tokens, latency, document id and redaction counts, never content; the investment links by number through the one linker every intake uses (`@pb/validation` linkInvestment: exact after normalization, never fuzzy, near misses and match guards as candidates by reason only), else by the exact company name the file name carries; the sponsor fund by exact name, canonical name or `core.fund_alias`; a confidence at or above `classifierConfidenceThreshold` runs `autoClassify`, below it `flagForReview` with the suggested type as a reason-only candidate and `doc_type` left null; a failed or refused call also flags for review. A `PdfError` leaves the row in NeedsReview with evidence `{ reason: 'unreadable', code }` and opens an `ops.data_exception` (source `documents`, rule `DOC-READ-01`); with the switch off the row stays Received with evidence `{ reason: 'classifier off' }`. A Classified quarterly_financials or capital_account_statement document sets `received_document_id` on its empty expected row (by investment or sponsor fund, period end and type), and generation (POST /expected-documents/generate, operations, system actor, idempotent, audited with counts) also matches rows against documents classified earlier: one quarterly_financials row per investment held at the period end whose deal type is co_invest_equity, cv_single_asset or cv_multi_asset (`QUARTERLY_REPORTING_DEAL_TYPES` in `documents/expected.ts`, a constant until the owner names its config key), one capital_account_statement row per sponsor fund with a commitment dated on or before the period end, due `expectedDueDaysAfterQuarterEnd` after it. Status and age are derived by `deriveExpected` in `documents/expected.ts` (received when matched; expected until `lateAfterDays` past the due date, late until `missingAfterDays`, missing after; age in days from the due date to the as-of day, or to the receipt day when received), which the monitoring board imports; the list judges rows as it reads them, filters on the derived status and pages on (due_date, id). The classify command (deal_team, operations) moves NeedsReview to Classified through `documentClassificationMachine` with the body's type (checked against the taxonomy) and links (checked under the caller's own row-level security, a 400 naming the field otherwise; a link left out keeps the classifier's), propagates the links to the duplicates and matches the expected row as the system actor, and is audited with before and after; docs/18 section 6 gives Received no manual transition, so a document indexed with the classifier off answers 409 until the table gains a Received > Classified row (open item). Lists page newest first on (indexed_at, id) with the common cursor, `q` runs `search_text @@ plainto_tsquery('simple', q)`, the review queue is NeedsReview, the detail adds the duplicates and the newest run, and the pages route reads the file from the store on demand (audited; a refusal is a 422 `unreadable-document` carrying the reader's code). Composition loads `<PB_DOCUMENT_ROOT>/truth/*.json` with `parseTruth` (a missing folder is no fixtures; a bad sidecar stops the process by name), registers `keywordClassifier` and `fixtureExtractor(truths)` on the MockAiClient, loads `config/extraction_schema.json` into the runtime (injection token `EXTRACTION_SCHEMAS`) and refuses to start on a bad `documents` or `extraction` block through `documentSettingsOf` and `extractionSettingsOf` (`documents/settings.ts`), the readers every service uses. Kill switches: `ai.classifier` gates classification as above; `ai.extraction` stays false in the database (migration 0003), the test harness turns it on through the flags endpoint as platform_admin (`startHarness({ enableFlags: ['ai.extraction'] })`, audited like any flag change) and `pnpm dev` users flip it in Admin > Flags. The harness generates the document set with `generateDocuments(dataset)` and writes the inbox files (both names of the duplicate pair) and one truth sidecar per content hash before the runtime is built, and exports the set as `harness.documents` for every suite.

## As built: the extraction API (wave 2)
`apps/api/src/extraction/` serves the five extraction routes. A batch (POST /extraction/batches, operations) is refused while `ai.extraction` is off (409 `kill-switch`, "AI extraction is switched off (ai.extraction)"), and names documents (read under the caller's own row-level security, so a document past their walls is not found) or a (period end, document type) selection read as the system actor over the whole book, Classified rows only; every document must be Classified (a NeedsReview, Duplicate or Received document is a 422 naming the file), indexed (M3 AC) and of a type an extraction schema covers (`config/extraction_schema.json`, quarterly_financials today; others answer 422 "no extraction schema for <label>"). The batch is an `ops.job` row (type `extraction_batch`, queued > running > succeeded or failed, progress to 100 either way, `runs_failed` when any run failed) with one Queued `doc.extraction_run` per document (investment and period copied from the document, schema id, prompt id and version from the registry), written as the system actor inside the caller's audited transaction, then driven inline by `extraction/runner.ts` with `batchConcurrency` workers over a small promise pool (Temporal is the production slot; each step is its own short transaction). Every state change goes through `extractionRunMachine` as the system actor and is audited by the caller: start (or retry from NeedsRetry) stamps `started_at` and reads the tokens of the other runs started that calendar day; past `dayTokenBudget` the run fails with `day_budget` before any call; otherwise the document is read from the store with the same reader and limits as the hub, every page is redacted, the input is built with `buildInput` (file name, content hash, page count, and the investment number and company name when linked) and the model is called with `outputSchemaFor(schema)`, logged by prompt id, version, model, tokens, latency, document id, run id and redaction counts, never content. An output that does not parse or an input `@pb/ai` refuses is a `schema` error, anything else the client throws is `transient`; each schedules a retry while its configured budget allows (the machine's own ceiling of one and three applies too), then fails. Tokens over `runTokenBudget` fail the run with `run_budget` (tokens and cost still recorded); cost is tokens per thousand times `costPerThousandTokensUsd`, to four places. Success runs `validateExtraction` over the redacted page texts with the bounds, the style of `config/style.json` (injection token `HIGHLIGHT_STYLE`, loaded at startup) and the document's period end, and stages one `stg.extracted_value` row per schema field with its validation state and findings (severity from the rule table; a quote clipped to the column's 150 characters) plus a `highlights` row (the JSON array as text) and a `commentary` row, which the detail returns as the narrative and the counts leave out. A failed run opens an `ops.data_exception` (source `extraction`, rule `EXT-RUN-01`). Runs and batches list newest first on (created_at, id) with the common cursor; the detail adds the document summary, the values in schema order with label, kind and requirement, and the page layouts read from the store on demand. The review commands (deal_team, operations, on a Succeeded, unapproved run the caller can see) accept, reject (reason on the audit event) or edit a value (the edit's unit is written to the row's `unit` column, since the table has no second unit column; a money field needs a money unit, other kinds take their own, and the value must fit it), `acceptClean` accepts every undecided clean row including the narrative, and `approve` refuses (409 `review-blocked`, naming the first) while a required field is not accepted or edited, an invalid value is not edited or rejected, or a flagged value is undecided, then promotes the final value of each target field (the edited value when edited), converted to dollars with `toDollars`, into `mon.quarterly_performance` for the final period end through the one promotion write the accounting import now also uses (`intake/promote.ts`, `promoteQuarterlyPerformance`: the quarter on record read again, the entry snapshot refused, update or insert, status approved, approver, time, reason, source document, source page of `revenue_ltm`, locator `field:revenue_ltm`, run id, prompt version, model id, audited with the figures before and after), as the system actor in the same transaction; the highlights and the commentary are written only when their rows are accepted, and a rejected or undecided target, or an accepted value the document did not state, leaves the record's column as it was. The run's `approved_by`, `approved_at` and `promoted_record_id` are then claimed on the row version the command read; a second approval and any later decision answer 409. `retry` drives a NeedsRetry run through the machine's own row; for a Failed run it queues a fresh run for the same document (same schema and prompt, no batch, requested by the caller) and drives it at once, since docs/18 gives the machine no Failed > Running row and a failed run stays on record as it failed. Kill switch as the documents section records: the harness turns `ai.extraction` on through the flags endpoint, `pnpm dev` users flip it in Admin > Flags.
