# 0013: Phase 3 plan: the controls (valuation workflow, capital activity and wires, change requests, closing and legal terms)
- **Status:** Accepted for the prototype (plan; as-built sections are appended as each wave lands)
- **Date:** 2026-10-25
- **Deciders:** repo owner (asked to continue along docs/09); built in Claude Code
## Context
Phases 0 to 2 are complete (decisions 0005 to 0012). docs/09 Phase 3 covers M10 (valuation workflow), M11 (deal change requests), M8 (closing workflow), M16 (capital activity: notices, funding, trade tickets, the wire register) and M22 (legal terms and allocation tie-out), with the exit: critical journeys 3, 4 and 6 of docs/12 pass and every forbidden transition in docs/18 has a passing rejection test. Today the valuation and capital notice commands exist only as simulated routes in the static preview (decision 0006; `packages/contracts/src/simulated.ts`), the machines exist in `packages/workflows` (valuation, capital notice, deal stage, deal change request), `mon.valuation` carries the lock guard trigger and the approval table, and `mon.capital_notice` and `mon.cash_flow` are read by the capital activity pages. There is no wire register, no trade ticket table, no change request table, and no `deal.*` table at all (the pipeline is a placeholder page). Journey 6 (a deal from Sourced to Closed with the diligence gate and the closing checklist) needs the deal stage commands and the closing workflow now, so the pipeline's record and its stage commands arrive in this phase as the M5 skeleton; the board, the pass history and the AI summary stay in Phase 5.
## Options considered
1. **Keep the commands simulated and build only the tables.** Fails the exit (the journeys run over the real API) and leaves the segregation-of-duties and wire controls untested where they matter.
2. **Serve the simulated routes for real and build the controls on the existing machines**, moving the three route definitions from the simulated table into the contract table so the web, the preview simulation and the API share one definition; add the wire register, trade tickets, change requests, the deal record with its stage commands, the closing record with its checklist, legal terms and the allocation tie-out; the preview keeps simulating every command client-side through the same transition tables.
3. **Build the full pipeline (M5, M7) now.** Wider than Phase 3; the board and the diligence templates belong to Phase 5 and would delay the controls.
## Decision
Option 2, in four waves on the Phase 2 pattern (non-overlapping worktree agents per wave, an adversarial review before publishing).

**Wave 1, foundation (parallel):**
- Migration 0013 and the schema mirrors: `mon.wire_instruction` (counterparty by sponsor fund or investment, version, bank details encrypted at the application layer with a key the environment provides (a mock key in the prototype, Key Vault in production), masked for every role but operations, callback fields: by, at, number source, result; active flag; a changed instruction is a new version), `mon.trade_ticket` (notice, amount, funding date, prepared by, approved by, the wire instruction version it was approved against, state), `mon.deal_change_request` (docs/03), `deal.opportunity`, `deal.opportunity_stage_history`, `deal.allocation`, `deal.diligence_task` (with a template per deal type in config), `deal.ic_decision`, `deal.closing` (opportunity, the investment on close, close date as the single source, operations confirmation), `deal.closing_item` (the required-document checklist from config), `deal.legal_term`; the taxonomies `change_type.*`, `legal_term_type.*`, `diligence_workstream.*`; row-level security (opportunities and closings carry the opportunity wall, change requests and tickets the investment wall; wire details readable by operations, approver, auditor, platform admin and the service actor only); the RLS matrix and the classification check extended. Config: `config/closing_checklist.json`, `config/diligence_templates.json`, `capitalActivity.urgencyPhrases` beside `wireChangeHoldDays`.
- Contracts: the valuation create and command routes and the capital notice command route move from `SIMULATED_ROUTES` to `ROUTES` (the preview reset route stays simulated); new routes for the valuation batch command, the wire register (list, detail masked, propose a version, record a callback), trade tickets (list, detail), change requests (create, list, detail, commands, the quarter-end check), opportunities (list, detail, create, stage commands, diligence task updates, IC decision, allocations), closings (detail, checklist item updates, confirm, close-date change, legal terms); the OpenAPI document regenerated.
- `packages/workflows`: a `wireInstructionMachine` (Proposed > Verified by a callback made by a person other than the proposer, Proposed > Rejected) and a `closingMachine` (Open > OpsConfirmed; a close-date change after confirmation returns it to Open with a reason) added to docs/18 with rejection tests; `valuationLockPayload` (the canonical JSON the lock hash covers) shared through `@pb/contracts` so the API (node:crypto) and the preview (SubtleCrypto) hash the same text.
- `tools/synthetic`: opportunities at every stage with stage history, diligence tasks, IC decisions and allocations; a closing record per existing investment (close date = entry date) and one in Closing for the journey with one checklist item open; legal terms; wire instructions per counterparty with the `wire_change` scenario as a second, unverified version; trade tickets for funded notices; change requests in every state; the seed loader and docs/14 extended.

**Wave 2, API:** `apps/api/src/valuations` (create a Draft, prepare, send back, deal-team approve, lock with the hash, reopen creating the next Draft version and an `ops.task` for the prior approvers, the batch command, approval rows, audit, the reporting-gate test proving reports read Locked only, open change requests on the valuation read), `apps/api/src/capital` (the wire register with masking and the callback by a second person, tickets drafted by operations and approved by a different person only when the active instruction is Verified and unchanged within the hold window, `wireChanged` returning an approved ticket to draft, funding confirmation, reconcile writing the approved cash flow with its notice and recalculating unfunded, the urgency flag from the notice document's text against the config phrases), `apps/api/src/change-requests` (create, route, start, apply with the applied period, reject with a reason, the quarter-end check opening a data exception per unapplied request), `apps/api/src/pipeline` (opportunities, stage commands through `dealStageMachine` with the diligence gate, the IC decision gate, the closing checklist and allocation tie-out gates, the conversion into `core.investment` on close with the data captured once, pass with a reason code), `apps/api/src/closing` (the closing record and its checklist, operations confirmation, the audited close-date change needing re-confirmation, legal terms, the allocation tie-out against the closing commitment).

**Wave 3, web and preview:** the valuations board's actions served for real with batch approval and the open change requests panel; the notice detail's actions for real with the ticket panel, the wire register page under Capital Activity with the masked instruction, the propose and callback forms; the change request form on the deal workspace and the operations queue; the Pipeline page (stage columns, opportunity detail with stage actions, diligence tasks, IC decision, allocations) and the deal workspace Diligence and Closing tabs (checklist, confirmation, legal terms); the preview simulating all of it; Playwright journeys 3, 4 and 6 and the accessibility scan on every new page.

**Wave 4:** adversarial review and fixes, docs (03, 09, 11, 14, 18, SESSION_LOG), gates, the artifact republished.
## Consequences (security, cost, operations, migration)
Security: SEC-5.6 (the preparer never approves: valuation lock, ticket approval), SEC-9.3 (a Locked valuation never changes in place: the trigger plus the API test), SEC-12.1 (bank fields never come from a document or a model), SEC-12.2 (versioned register, callback by a second person to an independently sourced number, logged), SEC-12.3 (dual control on tickets; no release on an unverified or recently changed instruction), SEC-12.4 (changed-instruction and urgency alerts on the notice), SEC-11.1 (every command audited with before and after). Cost: new tables and modules only; no dependency. Operations: the quarter-end check for unapplied change requests is a command operations runs (a scheduled job in production); alert dispatch for due dates stays pending (docs/11 C2). Migration: new tables and two columns on `mon.capital_notice` (the ticket and the urgency flag); `core.investment` gains nothing (the conversion writes the existing columns). Out of the prototype, recorded for the owner: Teams approval cards, the monthly new-deal confirmation, AI-assisted legal term extraction, field-level encryption through Key Vault (a mock key in the prototype), consent requests (M19).

## As built: the foundation (wave 1)
Migration `0013_controls.sql` adds the five enums, four taxonomy domains (`pass_reason`, `change_type`, `legal_term_type`, `diligence_workstream`), `mon.wire_instruction` (versioned per counterparty, bank details AES-256-GCM encrypted at the application layer through `packages/db/src/fieldCrypto.ts`, masked text beside them, the callback columns, one active Verified version per counterparty, the proposer never the caller), `mon.trade_ticket` (one per notice, approver never the preparer, the instruction version it was approved against), the two notice flags and funding columns, `mon.deal_change_request`, and the `deal` schema (`opportunity` with the opportunity wall, `opportunity_stage_history`, `diligence_task`, `ic_decision`, `allocation`, `closing` as the single source of every close date, `closing_item`, `legal_term`), with `pb.opportunity_visible` and `pb.closing_visible` for the children, history tables on the money-bearing ones, and 891 classified columns. `packages/contracts/src/controls.ts` and `routes-controls.ts` hold the shapes and the 29 control routes; `lock.ts` the canonical lock text; `packages/workflows` gains `wireInstructionMachine` and `closingMachine` (docs/18 sections 11 and 12) and the four new preconditions, every forbidden pair rejected in tests. `tools/synthetic/src/controls.ts` seeds the pipeline (a Closed opportunity per position plus twelve in flight), closings, legal terms, the register, tickets and change requests (docs/14 section 10). The config files `closing_checklist.json` and `diligence_templates.json` and the `capitalActivity` and `pipeline` additions drive the checklist, the templates, the urgency phrases, the due-soon window and the stage aging.

## As built: the API (wave 2)
`apps/api/src/valuations/workflow.service.ts` serves create, the commands, the batch and the version detail: the lock hash is the SHA-256 of `valuationLockText` (pinned in the contracts test and reproduced by `apps/api/src/common/lock.ts`), a reopen writes the next Draft version as the system actor inside the actor's transaction and an `ops.task` per prior approver, the batch runs id by id and never stops at a refusal, the reporting-gate test proves a DealTeamApproved mark changes no report and a lock does. `apps/api/src/capital/` serves the notice commands with the record the machine needs (`ticketExists`, `wireVerified`, `wireChangedWithinHold`: a version other than the active Verified one, not Rejected, proposed inside `wireChangeHoldDays`), the ticket drafted and re-drafted by operations and approved by another person against the active Verified version, `wireChanged` returning it to draft, funding and the reconcile writing the approved cash flow on the ticket's funding date; the register (`wires.service.ts`) proposes typed-by-hand versions, verifies on a second person's confirming callback and supersedes the previous active one, and decrypts for operations and approver only with each clear read audited; a new version sweeps the counterparty's notices as a system step (`apps/api/src/common/system-step.ts`, roles only, the actor kept). `apps/api/src/change-requests/` serves the form, the commands and the quarter-end check opening one `CR-QE-01` exception per unapplied request, idempotent. `apps/api/src/pipeline/` and `closing/` serve the opportunities with their gates computed from the same record the machine sees, the template tasks on first entering Diligence, IC decisions only at IC, allocations with the exact decimal tie-out, the closing opened on Approved to Closing with the config checklist, confirmation refused with the M8 and M22 messages, the audited close-date change needing confirmation again, legal terms captured and confirmed, and the conversion into `core.investment` with the data captured once and no figure invented; `information_schema` proves no other table carries a close date. One row-version module (`common/row-version.ts`, 412 `stale-row-version`) serves every controller.

## As built: the web and the preview (wave 3)
The valuations board carries the batch bar (deal team approve, approver lock, one result per id), every action live in every build (`lib/workflow.ts` no longer gates on the preview), the version screen with the approvals, the lock text and the reopen link, and the change request queue and form; the notice detail carries the alerts, the ticket panel with its release blockers in words, the draft ticket dialog and the live commands; the wire register and instruction pages (masked by default, clear details behind a toggle with the audit note, the callback form) and the trade tickets page; the pipeline board by stage with aging, the opportunity page (stage actions with the Approved to Closing dialog, gates, diligence tasks, IC decision, allocations editor, history) and the closing panel (items, confirmation with blockers, close date change, legal terms, tie-out) shared by the pipeline and the deal workspace Closing tab, with the Diligence tab reading the position's opportunity. The static preview simulates all of it through the same machines (`apps/web/src/preview/routes/{valuations,capitalNotices,wires,tickets,changeRequests,pipeline,closings,register}.ts`); the recordings carry no clear bank details for any credential (the simulated reveal reads the book), journeys 3, 4 and 6 run simulated in the route tests and for real in `apps/web/e2e/journey{3,4,6}.spec.ts`, and the probe walks the same paths on the built preview.
