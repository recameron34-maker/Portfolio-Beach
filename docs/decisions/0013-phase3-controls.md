# 0013: Phase 3 plan: the controls (valuation workflow, capital activity and wires, change requests, closing and legal terms)
- **Status:** Accepted for the prototype (plan; as-built sections are appended as each wave lands)
- **Date:** 2026-10-25
- **Deciders:** repo owner (asked to continue along docs/09); built in Claude Code
## Context
Phases 0 to 2 are complete (decisions 0005 to 0012). docs/09 Phase 3 covers M10 (valuation workflow), M11 (deal change requests), M8 (closing workflow), M16 (capital activity: notices, funding, trade tickets, the wire register) and M22 (legal terms and allocation tie-out), with the exit: critical journeys 3, 4 and 6 of docs/12 pass and every forbidden transition in docs/18 has a passing rejection test. Today the valuation and capital notice commands exist only as simulated routes in the static preview (decision 0006; `packages/contracts/src/simulated.ts`), the machines exist in `packages/workflows` (valuation, capital notice, deal stage, deal change request), `mon.valuation` carries the lock guard trigger and the approval table, and `mon.capital_notice` and `mon.cash_flow` are read by the capital activity pages. There is no wire register, no trade ticket table, no change request table, and no `deal.*` table at all (the pipeline is a placeholder page). Journey 6 (a deal from Sourced to Closed with the diligence gate and the closing checklist) needs the deal stage commands and the closing workflow now, so the pipeline's record and its stage commands arrive in this phase as the M5 skeleton; the board, the pass history and the AI summary stay in Phase 5.
## Options considered
1. **Keep the commands simulated and build only the tables.** Fails the exit (the journeys run over the real API) and leaves the segregation-of-duties and wire controls untested where they matter.
2. **Serve the simulated routes for real and build the controls on the existing machines**, moving the three route definitions from the simulated table into the contract table so the web, the preview simulation and the API share one definition; add the wire register, trade tickets, change requests, the deal record with its stage commands, the closing record with its checklist, legal terms and the allocation tie-out; the preview keeps simulating every command client-side through the same transition tables.
3. **Build the full pipeline (M5, M7) now.** Wider than Phase 3; the board and the diligence templates belong to Phase 5 and would delay the controls.
## Decision
Option 2, in four waves on the Phase 2 pattern (non-overlapping worktree agents per wave, an adversarial review before publishing).

**Wave 1, foundation (parallel):**
- Migration 0013 and the schema mirrors: `mon.wire_instruction` (counterparty by sponsor fund or investment, version, bank details encrypted at the application layer with a key the environment provides (a mock key in the prototype, Key Vault in production), masked for every role but operations, callback fields: by, at, number source, result; active flag; a changed instruction is a new version), `mon.trade_ticket` (notice, amount, funding date, prepared by, approved by, the wire instruction version it was approved against, state), `mon.deal_change_request` (docs/03), `deal.opportunity`, `deal.opportunity_stage_history`, `deal.allocation`, `deal.diligence_task` (with a template per deal type in config), `deal.ic_decision`, `deal.closing` (opportunity, the investment on close, close date as the single source, operations confirmation), `deal.closing_item` (the required-document checklist from config), `deal.legal_term`; the taxonomies `change_type.*`, `legal_term_type.*`, `diligence_workstream.*`; row-level security (opportunities and closings carry the opportunity wall, change requests and tickets the investment wall; wire details readable by operations, approver, auditor, platform admin and the service actor only); the RLS matrix and the classification check extended. Config: `config/closing_checklist.json`, `config/diligence_templates.json`, `capitalActivity.urgencyPhrases` beside `wireChangeHoldDays`.
- Contracts: the valuation create and command routes and the capital notice command route move from `SIMULATED_ROUTES` to `ROUTES` (the preview reset route stays simulated); new routes for the valuation batch command, the wire register (list, detail masked, propose a version, record a callback), trade tickets (list, detail), change requests (create, list, detail, commands, the quarter-end check), opportunities (list, detail, create, stage commands, diligence task updates, IC decision, allocations), closings (detail, checklist item updates, confirm, close-date change, legal terms); the OpenAPI document regenerated.
- `packages/workflows`: a `wireInstructionMachine` (Proposed > Verified by a callback made by a person other than the proposer, Proposed > Rejected) and a `closingMachine` (Open > OpsConfirmed; a close-date change after confirmation returns it to Open with a reason) added to docs/18 with rejection tests; `valuationLockPayload` (the canonical JSON the lock hash covers) shared through `@pb/contracts` so the API (node:crypto) and the preview (SubtleCrypto) hash the same text.
- `tools/synthetic`: opportunities at every stage with stage history, diligence tasks, IC decisions and allocations; a closing record per existing investment (close date = entry date) and one in Closing for the journey with one checklist item open; legal terms; wire instructions per counterparty with the `wire_change` scenario as a second, unverified version; trade tickets for funded notices; change requests in every state; the seed loader and docs/14 extended.

**Wave 2, API:** `apps/api/src/valuations` (create a Draft, prepare, send back, deal-team approve, lock with the hash, reopen creating the next Draft version and an `ops.task` for the prior approvers, the batch command, approval rows, audit, the reporting-gate test proving reports read Locked only, open change requests on the valuation read), `apps/api/src/capital` (the wire register with masking and the callback by a second person, tickets drafted by operations and approved by a different person only when the active instruction is Verified and unchanged within the hold window, `wireChanged` returning an approved ticket to draft, funding confirmation, reconcile writing the approved cash flow with its notice and recalculating unfunded, the urgency flag from the notice document's text against the config phrases), `apps/api/src/change-requests` (create, route, start, apply with the applied period, reject with a reason, the quarter-end check opening a data exception per unapplied request), `apps/api/src/pipeline` (opportunities, stage commands through `dealStageMachine` with the diligence gate, the IC decision gate, the closing checklist and allocation tie-out gates, the conversion into `core.investment` on close with the data captured once, pass with a reason code), `apps/api/src/closing` (the closing record and its checklist, operations confirmation, the audited close-date change needing re-confirmation, legal terms, the allocation tie-out against the closing commitment).

**Wave 3, web and preview:** the valuations board's actions served for real with batch approval and the open change requests panel; the notice detail's actions for real with the ticket panel, the wire register page under Capital Activity with the masked instruction, the propose and callback forms; the change request form on the deal workspace and the operations queue; the Pipeline page (stage columns, opportunity detail with stage actions, diligence tasks, IC decision, allocations) and the deal workspace Diligence and Closing tabs (checklist, confirmation, legal terms); the preview simulating all of it; Playwright journeys 3, 4 and 6 and the accessibility scan on every new page.

**Wave 4:** adversarial review and fixes, docs (03, 09, 11, 14, 18, SESSION_LOG), gates, the artifact republished.
## Consequences (security, cost, operations, migration)
Security: SEC-5.6 (the preparer never approves: valuation lock, ticket approval), SEC-9.3 (a Locked valuation never changes in place: the trigger plus the API test), SEC-12.1 (bank fields never come from a document or a model), SEC-12.2 (versioned register, callback by a second person to an independently sourced number, logged), SEC-12.3 (dual control on tickets; no release on an unverified or recently changed instruction), SEC-12.4 (changed-instruction and urgency alerts on the notice), SEC-11.1 (every command audited with before and after). Cost: new tables and modules only; no dependency. Operations: the quarter-end check for unapplied change requests is a command operations runs (a scheduled job in production); alert dispatch for due dates stays pending (docs/11 C2). Migration: new tables and two columns on `mon.capital_notice` (the ticket and the urgency flag); `core.investment` gains nothing (the conversion writes the existing columns). Out of the prototype, recorded for the owner: Teams approval cards, the monthly new-deal confirmation, AI-assisted legal term extraction, field-level encryption through Key Vault (a mock key in the prototype), consent requests (M19).

## As built: the foundation (wave 1)

The config files `closing_checklist.json` and `diligence_templates.json` and the `capitalActivity` and `pipeline` additions drive the checklist, the templates, the urgency phrases, the due-soon window and the stage aging.

## As built: the API (wave 2)
`apps/api/src/valuations/workflow.service.ts` serves create, the commands, the batch and the version detail: the lock hash is the SHA-256 of `valuationLockText` (pinned in the contracts test and reproduced by `apps/api/src/common/lock.ts`), a reopen writes the next Draft version as the system actor inside the actor's transaction and an `ops.task` per prior approver, the batch runs id by id and never stops at a refusal, the reporting-gate test proves a DealTeamApproved mark changes no report and a lock does. `apps/api/src/capital/` serves the notice commands with the record the machine needs (`ticketExists`, `wireVerified`, `wireChangedWithinHold`: a version other than the active Verified one, not Rejected, proposed inside `wireChangeHoldDays`), the ticket drafted and re-drafted by operations and approved by another person against the active Verified version, `wireChanged` returning it to draft, funding and the reconcile writing the approved cash flow on the ticket's funding date; the register (`wires.service.ts`) proposes typed-by-hand versions, verifies on a second person's confirming callback and supersedes the previous active one, and decrypts for operations and approver only with each clear read audited; a new version sweeps the counterparty's notices as a system step (`apps/api/src/common/system-step.ts`, roles only, the actor kept). `apps/api/src/change-requests/` serves the form, the commands and the quarter-end check opening one `CR-QE-01` exception per unapplied request, idempotent. `apps/api/src/pipeline/` and `closing/` serve the opportunities with their gates computed from the same record the machine sees, the template tasks on first entering Diligence, IC decisions only at IC, allocations with the exact decimal tie-out, the closing opened on Approved to Closing with the config checklist, confirmation refused with the M8 and M22 messages, the audited close-date change needing confirmation again, legal terms captured and confirmed, and the conversion into `core.investment` with the data captured once and no figure invented; `information_schema` proves no other table carries a close date. One row-version module (`common/row-version.ts`, 412 `stale-row-version`) serves every controller.

## Review fixes (wave 4): the API side
An adversarial review of waves 1 to 3 raised 45 findings. Its verdict journal was lost with a replaced sandbox (44 findings survive on record by id), so every finding was proven the other way round: a test that fails on the unfixed code first, then the fix. A finding that could not be reproduced is said so below. Five groups worked the API side in parallel, each in its own worktree.

**Capital activity and the wire register.** `systemStep` is re-entrant: it reads the roles on entry, does nothing when they are already the service role, and restores what it found, so a fund-level instruction version sweeps walled notices too (it answered 409 and rolled back before) and the step's own error surfaces instead of "current transaction is aborted". The reconciliation books the amount the ticket was approved and funded for, and the audit event and the notes name a difference from the notice. Inside the hold window after a verified change (`capitalActivity.wireChangeHoldDays`) the release needs a third person: neither the proposer of the changed version nor the person whose callback verified it may approve the ticket (two machine preconditions, one release blocker `verifier_within_hold`, docs/18 section 3). An older Proposed version is never verified over a newer Verified one (machine precondition, docs/18 section 11). A failed callback is recorded with its number source or not at all. The seed CLI encrypts with the key of the environment and refuses production without one. The notice detail keeps the register's rows (`activeWireInstruction`, the ticket's instruction) from roles the register refuses; alerts, the hold and the release check stay for every reader.

**Change requests and policies (migration 0014).** A quarter-end exception about a change request is read under the request's own policy, so a walled position's exceptions stay inside the wall. The quarter-end check scans every unapplied request as the system actor, opens one exception each and tells its runner how many it could not show (`hidden`). The owner named at route must be able to open the request: new definer `pb.user_inside_wall(entity, record, person)`, which answers only for a record the caller can see. The applied-in period cannot be after the quarter end the clock is in. A routed request names the person who routed it (`systemStep` keeps the actor); `asSystemActor` remains only on the scan nobody decides.

**Pipeline, closing and allocations.** A deal that reaches Closing again rewrites its closing (date and commitment) through a system step, returns a confirmed closing to Open through the machine's new `reopen` row and needs confirmation again; the audit reads the row as written. A confirmed closing is frozen: allocations and checklist items answer 422 until operations reopen it with a reason (new command `reopen`, audited, docs/18 section 12). The IC gate counts only decisions recorded since the deal last entered IC or left Passed (the recorded instant, not the typed committee date: the API clock is fixed at the as-of date and a committee a day before the record moved is legitimate); `gates.diligence.carriedOver` counts tasks done before a reopen. The tie-out sums received amounts only, and the refusal says how many are missing. Once the position exists, the close date changes only through a deal change request (`changeCloseDate` and `reopen` answer 422). `gates.closing.confirmed` says whether operations confirmed.

**Walls (migration 0016).** Converting a walled deal puts the position behind every wall of the deal in the same transaction: the service role may read wall rows and insert one for an investment, nothing else. The same migration fixes a defect found while probing: `read_member` on `core.walled_record` (migration 0006) compared the member row with itself through an unqualified `wall_id`, so a member of any wall read the wall rows of every wall; the walled records themselves stayed hidden. The access matrix now carries a second wall with no member and fails on the old policy.

**Valuations.** `PATCH /valuations/{id}` lets operations correct a Draft (method, inputs, fair value; audited; 409 from any other state), which is how a reopened version takes its corrected mark; the control routes are now 30. The lock text covers the method inputs (keys sorted at every depth), so two versions that differ only in inputs no longer share a hash. A fair value is `positiveMoney` (above zero, 18 integer digits and two decimals at most), refused with the field named and never echoed. Seeded Locked and Reopened versions carry the real SHA-256 of their lock text (`tools/synthetic` now depends on `@pb/contracts` for the one lock text). A version-number race answers 409, and a database error is logged by its code, constraint and table only, never the statement and its parameters. Open change requests on the valuation detail are empty outside the roles the change request list serves.

**Idempotency (migration 0015).** `ops.idempotency_key` and a global interceptor serve the `Idempotency-Key` header on every route the contract flags `idempotent`, read from the route table. A repeat with the same key, person, method, path and body replays the stored status, body and ETag with `Idempotency-Replayed: true` and runs nothing; another body under the same key is 422 `idempotency-key-reuse`; a malformed or empty key is 400; a repeat while the first is still running is 409 `idempotency-key-in-progress` (the key is reserved before the command runs; a refused command releases it). The stored request fingerprint is sealed with the field cipher, and bank details in clear are never stored: a replay of the two wire instruction routes carries `bankDetails: null`. The fingerprint uses the contracts' one `canonicalJson`. The route parity test now also compares every handler's role guard and sign-in with its contract route; it found no mismatch.

**Not changed, for the owner to decide.**
- D1-06, client-level allocation lines: the lines are read with the deal (client name masked for a reader without the entitlement, amounts visible), which wave 2 chose so that the deal team can allocate and everyone sees the same tie-out. Restricting the lines by client entitlement was tried and backed out: the tie-out then differs by reader, and a writer leaves lines they cannot read. It needs a decision on who may read client-level amounts on a deal, then a definer aggregate for the tie-out.
- Idempotency store: no purge and no replay window yet (rows are kept; classified operational, two years); the fingerprint is sealed with the wire register's field key, the only secret the API holds, where SEC-6.3 would want a separate key.
- The third-person rule counts a counterparty's first instruction as a change when it was proposed inside the hold window; narrow `recentVerifiedChange` if it should apply only to a replacement.
- The seeded wall has no operations member, so a walled change request can be routed but nobody can start or apply it (a seed gap the owner rule now makes visible).
- Two creates for period ends inside the same quarter tolerance can both start a chain (the second is refused only at lock); `POST /extraction/batches` is not flagged idempotent.

## Review fixes (wave 4): the web, the preview and the shared rules
Four groups followed the API fixes on the web side, each in its own worktree, test first.

**Shared rules instead of copies (D7-3, D7-2).** `packages/workflows` gains `controls-capital.ts` (business days, the hold window, the pending and the recent verified change, the notice alerts, the release blockers, who reads the register) and `controls-closing.ts` (the tie-out on received amounts, the missing-received refusal, the closing gates, the diligence gate with what was carried over a reopen, the IC decision round), pure functions the API and the static preview both call; `@pb/workflows` now depends on `@pb/calc`. `packages/contracts` gains `row-version.ts` (one If-Match parser, the ETag form, the texts of the 400 and the 412, and a conformance table run by the contracts, the API and the preview) and `idempotency.ts` (the key shape, the refusal texts, the canonical request body, what a stored answer may hold). A route that reads If-Match says so in the contract (`ifMatch` on seven routes), which the OpenAPI document, the preview and a test against the controllers read. A few thin compositions over those functions still exist on both sides, because they live in the capital service: the hold note, the three note sentences, the approval record keys and the booked amount of a reconciliation.

**The published preview carries no clear bank detail (WEB-1, W2-6).** `book.json` holds the masked form only, the build stops before it writes the book or the recordings if a full account number, routing code or reference of the dataset is in the text, and the probe scans every published text file. The simulated reveal shows the masked values with a note; details typed in the session are shown back to that session.

**Pages and simulation follow the API.** Capital: the register is restricted on the notice page for readers outside it, the third-person blocker in words, Verify disabled on an older Proposed version, the failed callback on the register row, the reconcile booking the ticket amount. Pipeline and closing: the confirmation as a gate, the frozen confirmed closing with Reopen for operations, the received-only tie-out, the close date fixed once the position exists, the carried-over count after a reopen, a simulated position behind the wall of its deal. Valuations and change requests: Edit draft for operations with If-Match, the method inputs on the detail (`valuationDetail.inputs`, now required in the lock text), `positiveMoney` in the dialogs, the board's prior mark after a reopen, who signed a seeded Locked version read from the row (the seed holds no decision rows, as the API answers), the hidden count of the quarter-end check, the owner-outside-the-wall and future-quarter refusals.

**The client.** A validation refusal names each field and what is wrong with it (WEB-4). The web sends an `Idempotency-Key` on every route the contract flags, one per action, kept while the outcome is unknown (five minutes at most) and dropped on an answer; the preview answers by the API's rules.

**Two API gaps the web wave found, fixed.** Every record a command guards with If-Match now answers its row version as the ETag (capital notices, tickets, wire instructions, opportunities and closings sent the framework's content tag, which the parser refuses as an If-Match). A body the server cannot read is answered in fixed words after the request has its id and its log line; the parser's message quoted the body.

**Judgment calls for the owner.** The client keeps a key for five minutes, so a deliberate identical second action inside that window gets the first answer; If-Match stays optional on the API (docs/17 asks for it on updates); seeded Locked versions have no decision rows, so the version screen names the signers from the row; exceptions about change requests show the raw entity name on the exceptions page (a label and a link are a small follow-up); the route dialog offers operations users only and the seeded wall has none.
